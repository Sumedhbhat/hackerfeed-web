HackerFeed server session map

This file explains the current WorkOS server-side session setup, the browser and Cloudflare Worker entrypoints, and how requests move through TanStack Start, tRPC, WorkOS, and the database layer.

Open directly in browser Browser Server Cloudflare WorkOS Postgres

1. Overview

The app is a TanStack Start SSR React app. Locally it runs through Vite. In production it deploys as a Cloudflare Worker. Auth is now centered around a server-owned WorkOS sealed session cookie, and client code asks the server who the current user is.

Browser Loads HTML, hydrates React, calls session and tRPC APIs.
Worker Cloudflare runs the TanStack Start server entry.
Routes TanStack Router handles pages and server route handlers.
Services Auth, tRPC, favorites, users, and database modules.
External systems WorkOS for auth, Postgres for app data, Sentry for errors.
Current mental model WorkOS proves who the user is. The server stores that proof in an HttpOnly sealed session cookie. React does not own the session.

2. Entrypoints

Browser entry

src/client-entry.tsx

This runs after the browser receives server-rendered HTML. It initializes browser Sentry when VITE_SENTRY_DSN exists, wraps React with a Sentry error boundary, then hydrates <StartClient />. 

HTML from server
-> src/client-entry.tsx
-> optional Sentry browser init
-> hydrateRoot(document)
-> StartClient
-> interactive React app
Server entry

src/server-entry.ts

This is the server runtime entry configured in Vite. On Cloudflare it becomes the Worker request handler. It wraps TanStack Start's handler with Sentry and a custom unhandled-error response path. 

Request
-> Cloudflare Worker fetch
-> Sentry.withSentry(...)
-> handleFetch(request)
-> TanStack Start handler
-> route render or API response

What the server error wrapper does

1
Try normal app handling startFetch(request) handles SSR pages and API routes.
2
Capture unexpected failures Sentry receives the exception with request tags and an error id.
3
Return the right kind of 500 API requests get JSON. Page requests get a small HTML error page.

3. Cloudflare setup

Cloudflare integration is split between vite.config.ts and wrangler.jsonc.

vite.config.ts

The plugin stack does the build-time wiring:

  • cloudflare({ viteEnvironment: { name: "ssr" } }) targets the SSR build at Cloudflare.
  • tanstackStart(...) points to custom client and server entries.
  • tsconfigPaths() enables #/* imports.
  • tailwindcss() enables Tailwind styles.
  • viteReact() enables React and the React Compiler Babel plugin.

wrangler.jsonc

Wrangler describes the deployed Worker:

  • Worker name: hackerfeed-web
  • Compatibility flag: nodejs_compat
  • Observability is enabled.
  • Sentry, WorkOS, and app vars are listed.
  • D1 bindings are present, but see the storage note below.
Important storage note wrangler.jsonc includes D1 bindings named DB and hackerfeed. The current database client in src/server/database/client.ts still uses Prisma with DATABASE_URL, which means the active app data path is Postgres unless more D1-specific code is added later.

4. WorkOS server-side session flow

The core file is src/server/auth/session.ts. It creates WorkOS URLs, handles callback exchange, seals the session into a cookie, reads the current session, refreshes it when possible, and signs users out.

Start sign-in

The browser goes to /auth/sign-in?returnTo=/some-page. The server asks WorkOS for a PKCE authorization URL.

Store short auth-flow cookie

The server stores codeVerifier, state, and returnTo in hackerfeed_auth_flow.

Redirect to WorkOS

The browser leaves HackerFeed and completes authentication at WorkOS.

Callback returns

WorkOS redirects to /auth/callback?code=...&state=.... The server validates the stored state before exchanging the code.

Set sealed session

WorkOS returns a sealed session. The server stores it in the HttpOnly hackerfeed_session cookie.

Return to app

The browser is redirected to the original safe returnTo path.

Cookie: hackerfeed_auth_flow

Short lived. Exists only while the user is in the WorkOS login flow. It protects the callback by preserving PKCE and state data.

Cookie: hackerfeed_session

Longer lived. HttpOnly. Contains the WorkOS sealed session. The server loads and validates it on future requests.

Auth route handlers

Route Server function Purpose
/auth/sign-in createSignInResponse Starts WorkOS PKCE auth and redirects to WorkOS.
/auth/callback createAuthCallbackResponse Exchanges WorkOS code and sets the sealed session cookie.
/auth/sign-out createSignOutResponse Clears local cookie and redirects through WorkOS logout if possible.
/api/auth/me createSessionJsonResponse Returns the current user JSON to client hooks.
Why the missing env vars caused a 500 WORKOS_API_KEY and WORKOS_COOKIE_PASSWORD are required by src/env.ts and by the WorkOS session module. If either is missing, environment validation fails before the server can render normally.

5. Client auth state

The client-facing auth hook is src/hooks/useAuthSession.ts. It does not own the WorkOS session. It asks the server for session state.

1
React mounts useAuthSession() subscribes to a small module-level cache.
2
Fetch current user The hook calls /api/auth/me with same-origin credentials.
3
Server reads cookie The server authenticates or refreshes the sealed WorkOS session.
4
UI gets user or null Components use this state for menus, guards, favorites, and migration. 
signIn(returnTo) -> window.location.assign("/auth/sign-in?returnTo=...")
signOut()       -> window.location.assign("/auth/sign-out")

6. tRPC and favorites backend

The route src/routes/api/trpc/$.ts sends tRPC requests to src/server/trpc/handler.ts. The handler creates the router once and creates request context per request.

Favorite click useFavorites updates UI optimistically.
tRPC client Calls /api/trpc.
Context Server decides who the current user is.
Router Protected procedure rejects missing users.
Service Favorites service writes through repositories.
Router change in this cycle createAppRouter() now lazy-imports the favorites service. That avoids importing the database/service layer as soon as the router module is loaded, which is friendlier to server bundling and Cloudflare runtime constraints.

7. Data storage

The Prisma schema currently defines three app concepts:

AppUser

One local app user per stable WorkOS user id.

Story

Shared Hacker News story records keyed by HN story id.

Favorite

A relation connecting an app user to a story.

src/server/database/client.ts creates a Prisma client with @prisma/adapter-pg and process.env.DATABASE_URL.

Local database state from inspection The local Postgres connection worked, but the selected database had no app tables at that time. Run migrations before expecting backend favorites to persist locally.

8. Environment variables

Variable Used by Secret? Notes
DATABASE_URL Prisma/Postgres Yes Required for local database-backed favorites.
WORKOS_API_KEY WorkOS server SDK Yes Required. Missing value causes env validation failure.
WORKOS_COOKIE_PASSWORD WorkOS sealed sessions Yes Required. Must be at least 32 characters.
VITE_WORKOS_CLIENT_ID WorkOS auth flow Treat as deploy secret Client id used in auth URLs and JWKS lookup.
VITE_WORKOS_API_HOSTNAME WorkOS SDK No Usually api.workos.com.
VITE_WORKOS_REDIRECT_URI WorkOS dashboard and app No Must match local or deployed callback URL.
SERVER_URL Server origin helper No Optional. Overrides origin used for callback/logout URLs.
SENTRY_DSN Server Sentry Usually yes Optional. Prefer Cloudflare secret.
VITE_SENTRY_DSN Browser Sentry No Optional and exposed to the browser.
WORKOS_JWT_AUDIENCE Bearer-token verifier No Optional in current schema. Relevant to token-based auth verification.
Rule of thumb Anything not prefixed with VITE_ should be treated as server-only. Anything containing API keys, passwords, sessions, or database URLs should not be committed.

9. Runbooks

Local setup

bun install
bun run dev

Minimum local env shape:

DATABASE_URL="postgresql://..."
WORKOS_API_KEY="sk_test_..."
WORKOS_COOKIE_PASSWORD="generated-32-plus-char-secret"
VITE_WORKOS_CLIENT_ID="client_..."
VITE_WORKOS_API_HOSTNAME="api.workos.com"
VITE_WORKOS_REDIRECT_URI="http://localhost:3000/auth/callback"

Generate a cookie password:

openssl rand -base64 32

Apply database migrations when needed:

bun run db:migrate

Cloudflare deploy

wrangler secret put WORKOS_API_KEY
wrangler secret put WORKOS_COOKIE_PASSWORD
wrangler secret put VITE_WORKOS_CLIENT_ID
wrangler secret put SENTRY_DSN
bun run deploy

SENTRY_DSN is optional. WorkOS redirect URLs in the WorkOS dashboard must include the deployed /auth/callback URL.

Verification

bun run test
bun run check

10. What happens right now?

1
A user opens HackerFeed Cloudflare Worker receives the request in production, or Vite handles it locally.
2
The server entry handles the request Sentry wraps the request and TanStack Start renders a page or API response.
3
The browser hydrates React client-entry.tsx initializes optional browser Sentry and hydrates StartClient.
4
Client loads auth state useAuthSession calls /api/auth/me. The server reads the sealed WorkOS cookie.
5
If signed in, favorites use the backend tRPC protected procedures call the favorites service, which writes through Prisma/Postgres.
6
If signed out, local favorites still work The browser-side favorites store remains the fallback until a user signs in and migration runs.
