HackerFeed · Implementation plan

Story and paper view activity

Record deliberate content-opening clicks from signed-in users as durable D1 rows—without delaying navigation, collecting anonymous activity, or building reporting before it is needed.

Proposed Storage only No implementation yet
Outcome Scope Data model Write flows Sequence Verification Deferred

Desired outcome

One row for every intentional open

A view is an explicit click on the primary story or paper link. The resulting activity is durable, append-only, and associated with the authenticated app user and stored content.

What gets recorded

Story title clicks, primary Read article/Open post actions, and paper-title clicks from signed-in users.

What never changes

The article or paper opens immediately. Tracking is background work and cannot block, delay, cancel, or replace navigation.

Resolved decisions

Small, deliberate scope

  • Signed-in users only; no anonymous tracking.
  • Every qualifying click inserts a new view row.
  • Views are retained indefinitely with no cleanup job.
  • Favorites are excluded and remain represented by existing data.
  • No routes, trace IDs, request IDs, email, or session metadata.
  • No dashboards, reports, admin pages, or read APIs in this phase.
  • No period start/end columns and no history tables.
  • No cascading deletion of referenced users or content.
Not a view: card rendering, feed prefetching, scrolling, feed loading, abstract expansion, Discuss, Project, Code, or favorite actions.

Data model

Two tables with real foreign keys

Separate tables avoid a polymorphic content reference and let D1 enforce the connection to either a story or paper.

story_views

ColumnPurpose
idGenerated automatically by the table's uuidPrimaryKey() default
appUserIdForeign key to app_users.id
storyIdForeign key to stories.id
viewedAtDatabase-generated UTC click timestamp
lastUpdatedDateDatabase-generated UTC audit timestamp
lastUpdatedByPlain-text internal user ID; not a foreign key

paper_views

ColumnPurpose
idGenerated automatically by the table's uuidPrimaryKey() default
appUserIdForeign key to app_users.id
paperIdForeign key to hf_papers.id
viewedAtDatabase-generated UTC click timestamp
lastUpdatedDateDatabase-generated UTC audit timestamp
lastUpdatedByPlain-text internal user ID; not a foreign key
Identity rule: the server derives appUserId and lastUpdatedBy from the authenticated session. The browser cannot supply or override either value.
Indexes: index each table by user and time, and by content and time. Do not add a user/content uniqueness constraint because repeat clicks are separate views.

Runtime behavior

Open first; track in the background

Step 1User clicks

A qualifying primary story or paper control is activated.

Step 2Dispatch once

An authenticated mutation starts without awaiting or automatic retry.

Step 3Insert view

The insert omits the ID; the primary-key default generates it automatically.

Step 4Open content

External navigation runs immediately and independently.

Story write

  1. Resolve the authenticated app user.
  2. Upsert the validated Hacker News story using existing persistence behavior.
  3. Resolve its local stories.id.
  4. Insert story_views in the same transaction.

The insert omits id, allowing uuidPrimaryKey() to generate it automatically.

Paper write

  1. Resolve the authenticated app user.
  2. Find the existing paper by stable arXiv ID.
  3. Insert paper_views.

A missing paper fails tracking silently and never creates an incomplete paper or blocks the external link.

Failure contract: send one best-effort write with no automatic retry, show no tracking error in the UI, and preserve synchronous popup creation for story links.

Implementation sequence

Build from storage to click wiring

  1. Schema and migrationAdd both Drizzle tables, restrictive foreign keys, database timestamp defaults, and future-friendly indexes.
  2. RepositoriesInsert story and paper views without supplying IDs, allowing the primary-key defaults to generate them.
  3. Service boundaryResolve the authenticated app user, reuse story persistence, resolve papers, and own transaction behavior.
  4. Write-only mutationsAdd validated authenticated tRPC mutations; add no list or reporting procedure.
  5. Browser helperDispatch once without awaiting or retrying, and suppress tracking errors.
  6. Click wiringAttach tracking only to story titles/primary actions and paper titles.
  7. Focused verificationCover schema, transactions, authentication, backend IDs, click qualification, and navigation independence.

Success criteria

Done means behavior—not just rows

  • Signed-out clicks open content and write nothing.
  • Each signed-in qualifying click creates exactly one corresponding view row.
  • An absent story and its view are saved atomically.
  • A paper view references the already-ingested paper.
  • Two deliberate clicks create two rows.
  • A failed write is not retried automatically or exposed in the UI.
  • Non-qualifying rendering and secondary actions create no views.
  • Network or server failures never disrupt external navigation.
  • User identity is always derived server-side.
  • Referenced users and content cannot be cascade-deleted.

Explicitly deferred

Useful later, intentionally absent now

Reporting and monitoring
Reading stored activity, active-user definitions, admin interfaces, reports, aggregation, dashboards, and analytics exports.
Observability integrations
Grafana, Sentry, OpenTelemetry, traces, request IDs, and correlation identifiers.
