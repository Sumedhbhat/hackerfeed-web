## Architecture

**Framework stack:** TanStack Start (SSR React framework) + TanStack Router (file-based routing) + TanStack Query (data fetching) + TanStack Store (client state). Deployed to Cloudflare Workers via `@cloudflare/vite-plugin`.

**Path alias:** `#/*` maps to `src/*` (configured in `package.json` `imports` and `tsconfig.json`).

### Data flow

The feed page (`src/routes/index.tsx`) uses a two-layer query model:
1. **Layer 1** — `feedStoryIdsQueryOptions(feed)` fetches the full list of story IDs for the active feed (top/new/best). Stale after 60s.
2. **Layer 2** — `storyItemQueryOptions(storyId)` fetches each story individually and progressively. Stale after 5 min.

The route loader (`loader` in `index.tsx`) SSR-prefetches the ID list and warms the cache for the first `PAGE_SIZE` items. On the client, switching tabs or loading more items fetches incrementally without resetting previously loaded tabs.

All HN API calls go through `src/lib/hacker-news/queries.ts` (direct calls to `hacker-news.firebaseio.com`). Normalization (`normalizeStoryItem`, `normalizeStoryIds`) strips dead/deleted items and coerces types before anything touches React.

### Favorites

`src/lib/favorites-store.ts` is a `@tanstack/store` instance that persists to `localStorage` under `hackerfeed:favorites`. It stores the full `HackerNewsStoryRecord` (not just IDs) so favorites render without re-fetching. Actions: `toggleFavorite`, `isFavorited`, `getFavorites`, `clearAllFavorites`. Subscribe with `useStore(favoritesStore, selector)` in components.

### Auth

WorkOS AuthKit owns the session entirely in the browser (`src/integrations/workos/provider.tsx`, `devMode` keeps the refresh token in localStorage). There are no HackerFeed session cookies. `SessionGate` in `__root.tsx` sends signed-out users to WorkOS; only `/auth/callback` and `/auth/signed-out` are public. API calls (tRPC, `src/lib/ai/client.ts`) send `Authorization: Bearer <access token>` via `getAuthHeaders()` in `src/lib/auth/authkit.ts`; the server verifies it against WorkOS's JWKS with `getRequestUser()` in `src/server/auth/workos-access-token.ts`.

### Feature flags

Flags are code, not a service. `src/server/feature-flags/config.ts` defines them, `GET /api/feature-flags` returns them for the requesting session, and `SessionGate` in `__root.tsx` holds the app until the auth state and that session's flags are both known. Read flags with `useFeatureFlag(name)` on the client, and enforce them with `isFeatureEnabled(name, user)` on the server. Follow `.claude/skills/feature-flags/SKILL.md` to add, target or remove a flag.

### Logging and debugging

Use `logger` from `#/lib/logger` everywhere (browser and Worker), never `console.*`. Each call goes to Sentry Logs (structured, linked to the trace) and the console. Pass the caught value as `error`: `logger.error(msg, { error })` also creates a Sentry issue. Use `warn` where you log and rethrow, so only the code that handles the error reports it. Error screens show the trace ID (`useErrorReport` + `TraceIdNote`). To debug a report, search `trace:<id>` in Sentry for the issue, logs and browser→Worker spans.

### Routing

Routes live in `src/routes/`. `routeTree.gen.ts` is auto-generated by the TanStack Router Vite plugin — do not edit it manually. Add new routes by creating files in `src/routes/`; the plugin regenerates the tree on the next dev-server restart or build.

The root layout (`src/routes/__root.tsx`) wraps every page in `TanStackQueryProvider`, `AppShell`, `SiteHeader`, and `SiteFooter`. It injects a blocking inline script to resolve the dark/light/auto theme before first paint to avoid flash-of-wrong-theme.

### UI components (atomic design)

Every component lives in one of four layers under `src/components/`. Read a file top-down and it should say *what* is on screen; *how it looks* lives only in the bottom two layers.

| Layer | What goes here | Styling (`className`/`style`) | Data / hooks |
|---|---|---|---|
| `atoms/` | One styled element: `Button`, `ButtonLink`, `TextLink`, `Text`, `Heading`, `Kicker`, `Stack`, `Row`, `Card`, `Panel`, `PageContainer`, `Skeleton`, `Icon`, `Avatar`, `TextInput`… | Yes, the only place Tailwind classes are written | No |
| `molecules/` | A few atoms composed into a reusable piece: `TabList`, `EmptyState`, `StatusPanel`, `BackLink`, `MetaLine`, `LoadingScreen`… | Yes, layout glue only | No, props in, callbacks out |
| `organisms/<feature>/` | A feature section with behavior: `StoryCard`, `SiteHeader`, `Comment`, `PapersFeed`… | **No** | Yes |
| `pages/` | The full body of one screen, rendered by a route: `FeedPage`, `StoryPage`, `PapersPage`… | **No** | Yes |

Routes in `src/routes/` stay thin: route config, loader, search params, then render a page. They follow the same rule as pages.

Interactive atoms are built on [Base UI](https://base-ui.com) (`@base-ui/react`), which supplies the keyboard, focus and ARIA behavior; the atom adds the Tailwind look. Its docs ship in `node_modules/@base-ui/react/docs/`.

| Need | Atom (Base UI part) |
|---|---|
| Button | `Button` (`Button`). Links that look like buttons stay `<a>`: `ButtonLink`, `ExternalButtonLink` |
| On/off button, pick-one chips | `ToggleButton`, `ToggleGroup` (`Toggle`, `ToggleGroup`) |
| Tabs | `Tabs`, `TabList`, `Tab`, `TabPanel` (`Tabs`) |
| Drop-down menu | `Menu`, `MenuTrigger`, `MenuPopup`, `MenuGroup`, `MenuItem`, `MenuLinkItem` (`Menu`) |
| Dropdown field | `Select`, `SelectLabel`, `SelectTrigger`, `SelectOptions` (`Select`) |
| Show/hide | `Collapsible`, `CollapsibleTrigger`, `CollapsiblePanel` (`Collapsible`) |
| "Are you sure?" | `AlertDialog*` atoms, composed by the `ConfirmButton` molecule (`AlertDialog`) |
| Picture or initials | `Avatar` (`Avatar`) |
| Text input | `TextInput` (`Input`). `TextArea` is native: Base UI has none |

These atoms manage their own ARIA state: pass `value`, `pressed` or `open`, never `aria-selected`/`aria-pressed`/`aria-expanded` by hand. A toggle keeps one label while pressed (`aria-label="Save to favorites"` + `pressed`). Never use `window.confirm`; use `ConfirmButton`. For a new interactive pattern, check whether Base UI has the component and wrap it in a new atom.

Before building UI, list `src/components/atoms/` and `src/components/molecules/` and reuse what is there. Add a variant to an existing atom before adding a new atom.

Rules, enforced by Biome (`bun run check`) and guarded by `src/test/lint-rules.test.ts`:
- `lint/no-styling-outside-atoms.grit` rejects `className`, `class`, `style` and spreads that carry them in every `.tsx` file outside `atoms/` and `molecules/`, including new folders. If no component fits, add an atom/molecule (or a variant) instead of styling inline.
- `noRestrictedElements` rejects raw `<button>`, `<a>`, `<input>`, `<textarea>`, `<select>`, `<h1>`–`<h6>`, `<p>`, `<img>` and `<style>` everywhere outside atoms/molecules. Each diagnostic names the atom to use.
- `noRestrictedImports` stops atoms and molecules from importing `#/hooks`, `#/lib`, `#/server` or higher layers, so they stay presentational. It also stops everything outside `atoms/` from importing `@base-ui/*`.
- Exempt (in `biome.json` overrides, never inline): tests, and the stylesheet-free error UI in `client-entry.tsx`, `router.tsx` and `src/server/errors/`.

When a rule blocks you, change the component, not the rule. Do not edit `biome.json` or `lint/`, add `biome-ignore` for these rules (the test fails on it), restyle elements from `src/styles.css`, or move files to dodge a rule. If the request can't be met within the layers, stop and say so. Colors come from the CSS variables in `src/styles.css` (`--lagoon`, `--sea-ink`…); add a token there rather than using raw Tailwind palette colors or hex values.

Prefer props that describe intent (`tone="soft"`, `size="page"`, `variant="accent"`) over props that leak CSS. Tests that mock `@tanstack/react-router` must provide `createLink` (see `src/test/createLinkMock.tsx`), because the link atoms are built with it.

### Testing

Vitest is configured with two projects (`vitest.config.ts`):
- **`node`** — pure utility and store tests (`src/**/*.test.{ts,tsx}`, excluding `src/components/**` and `*.browser.test.*`)
- **`browser`** — component and browser-API tests using `happy-dom` (`src/components/**/*.test.*` and `src/**/*.browser.test.*`)

Use the `.browser.test.ts` suffix for anything that touches `window`, `localStorage`, or DOM APIs.

Base UI in tests: keyboard focus moves a tick after the key press, so wrap focus assertions in `waitFor`. A select option only takes a mouse click that started on it: `fireEvent.pointerDown(option, { pointerType: "mouse" })`, then `fireEvent.click(option)` (see `choose()` in `StoryChatPage.test.tsx`). Popups render in a portal, so query them from `screen`.
